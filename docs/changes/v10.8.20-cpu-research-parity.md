# API v10.8.20 — Reproduce the historical CPU parity regime

## Why this version exists

The previous parity work over-corrected the research runtime by forcing
`deterministic_execution=true` and `LightGBM n_jobs=1`.

Review of the September 2026 transition from the ~US$5.5M Control to the
~US$10M Control shows that the decisive 10.8.83 -> 10.8.84 change was the
compute backend, not a deterministic-runtime rewrite.

Historical sequence recovered from the project conversation:

```text
10.8.83
GPU
same RAW snapshot / same features / same folds / same hyperparameters
Control ≈ US$4.15M
Soft ≈ US$4.49M

10.8.84
CPU
same snapshot reused byte-for-byte
same strategy
same folds
same hyperparameters
deterministic_execution=false
LightGBM n_jobs=-1

Control = US$10,094,316.30
Soft    = US$9,851,632.93
Soft changed base actions = 5
```

The fold calibration also changed:

```text
GPU 10.8.83: 0.01 / 0.01 / 0.00
CPU 10.8.84: 0.00 / 0.01 / 0.00
```

The first important OOS divergence occurred around 2020-07-28.

## What remains unchanged from 10.8.18/10.8.19

The following parity work remains:

- full Alpaca RAW refresh during Simulation;
- RAW SIP daily bars;
- complete Corporate Actions refresh;
- DOC structural exclusion to PEAK;
- homologated pre-ex-date split normalization;
- no dividend adjustment to model OHLCV/features/targets;
- 55 eligible assets from the 56 configured assets;
- calibration candidate score diagnostics;
- Model Tuning remains database-only after freezing the Simulation snapshot.

## Runtime correction

Research Simulation now restores the homologated CPU regime:

```text
device_type = cpu
deterministic_execution = false
LightGBM n_jobs = -1
early_stopping_enabled = false
numeric_thread_limit remains the configured value
```

The API already instantiates the LightGBM research model with
`device_type="cpu"`, so GPU cannot be selected on this path.

## LightGBM package version

The exact installed LightGBM package version used by historical 10.8.83 and
10.8.84 was not recorded in the recovered artifacts.

Therefore 10.8.20 removes the speculative `lightgbm==4.6.0` pin introduced in
10.8.19 and restores the compatible range:

```text
lightgbm>=4.6,<5
```

The current run-time version is still recorded in every exported result.
