## Quarto incremento revisado: /docs com download NOVO da Alpaca e dados próprios do MCT
O primeiro desenho do endpoint consumia CSV congelado do TCC. O usuário corrigiu a necessidade: o MCT deve baixar seus próprios dados atuais, criar a pasta dados automaticamente e registrar o snapshot local. A implementação abaixo **substitui** a configuração anterior do endpoint. O CLI científico antigo permanece como ferramenta auxiliar e não é usado por essa API.

- Admin-only: `/api/admin/control-shadow`, integrado em `main.py` com `require_admin_session`, bloqueando Viewer e Reviewer.
- `POST /jobs` (HTTP 202) com `confirm=REFRESH_ALPACA_CONTROL_SHADOW_NO_ORDERS`, posição hipotética (`current_asset`) e `holding_sessions`. Os parâmetros não permitem informar caminho de arquivo, conta ou Strategy. É sempre um download novo; não lê o snapshot do TCC.
- O job fixa a última sessão XNYS concluída com margem de segurança de 20 minutos, baixa todo o histórico diário do universo Control da Alpaca (feed SIP, adjustment RAW, 1Day, desde 2016-01-01), consulta Corporate Actions até a mesma sessão, normaliza splits e exclui ativos com mudança estrutural de identidade registrando a razão no manifesto.
- Sem fallback silencioso para IEX, séries ajustadas por dividendos, Mongo cache ou séries antigas. Falhas de provedor e ausência de barras de ativos não estruturalmente excluídos fazem o job falhar sem gerar uma decisão.
- Pasta criada pelo próprio processo, se necessário, abaixo da raiz da API: `dados/control_shadow/snapshots/<job_id>/`. Cada snapshot completo guarda `raw_bars/*.csv`, `corporate_actions/*.json`, `normalized_bars/*.csv` e `manifest.json` com hashes SHA-256, parâmetros, sessões, fonte e exclusões. O diretório temporário só é publicado após a gravação completa, sem sobrescrever snapshots anteriores. `/dados/` entra no `.gitignore`.
- A construção de painel, treinamento LightGBM, calibração cronológica e decisão sem ordens continuam reutilizando o Control científico. Os dados novos **não garantem** retorno idêntico ao snapshot antigo. O resultado inclui caminhos locais, identidade do snapshot, utilidades e janelas de treinamento.
- Logs por ativo e progresso de modelo aparecem no console Uvicorn/PyCharm e na coleção Mongo isolada `control_shadow_jobs`, sem escrever em coleções de Winner, carteira, Strategy #28, Backtest ou ordens. `GET /jobs/{job_id}` apresenta status e resultado; `GET /jobs/{job_id}/logs` acompanha o processamento.
- Exclusivamente local/de desenvolvimento, desabilitado por padrão: somente `MCT_CONTROL_SHADOW_API_ENABLED=true` no `.env` da API. **Não** configurar `MCT_CONTROL_SHADOW_FROZEN_ROOT`; o novo endpoint ignora essa variável e não usa o TCC.
- `API_VERSION` na branch segue `10.8.39`. A versão operacional em produção reportada pelo usuário permanece `10.8.38` (Front `10.7.16`). Não efetuar merge/deploy/promover a Strategy #28 por esta entrega.

### Execução no PyCharm: só a API
Na raiz do repositório MCT API:
```powershell
git fetch origin
git switch feature/v10.8.39-control-operational-parity
git pull --ff-only origin feature/v10.8.39-control-operational-parity
$env:PYTHONPATH = (Resolve-Path .\\src).Path
python -m unittest discover -s tests -p "test_control_shadow*.py" -v
```
No `.env` da API, configure apenas:
```dotenv
MCT_CONTROL_SHADOW_API_ENABLED=true
```
Reinicie a API com **um worker e sem hot reload durante o job**, autentique-se como admin e abra `http://localhost:8000/docs`. Em **Control Shadow — no orders**, inicie POST `/api/admin/control-shadow/jobs`:
```json
{"confirm":"REFRESH_ALPACA_CONTROL_SHADOW_NO_ORDERS","current_asset":"CASH","holding_sessions":0}
```
Copie o `job_id`; use GET `/api/admin/control-shadow/jobs/{job_id}/logs` e o console do PyCharm para progresso. GET `/api/admin/control-shadow/jobs/{job_id}` apresenta decisão e pasta snapshot quando o status for `completed`. O download e a criação da pasta acontecem no computador em que **essa instância da API** está rodando, não no navegador. É necessário ter credenciais Alpaca com acesso ao feed SIP. O sistema não envia ordens de compra/venda.

### Limites
- O snapshot é uma captura nova da fonte; não sobrescreve os CSVs científicos do TCC nem altera a carteira.
- O Control gerado é apenas ensaio da **última sessão completa**. A equivalência operacional histórica por sessão e a integração à cadeia real Trader continuam pendentes.
- O sistema não registra pedidos para envio de ordens, não promove Winner nem altera seleção de Strategy. Evitar múltiplos workers e reinicialização durante o job, pois execução em thread não sobrevive ao reinício do processo.
