# v10.8.27 — TCC frozen data parity audit (read-only)

## Cause / question

Strategy #11 and Strategy #12 have the same MCT market-data signature
(`d954b251...`) and nearly identical Control paths, while the official TCC
frozen Control selects Fold-1 margin 0.0 instead of 0.01. Merely copying the
v1.0.6 engine into MCT did not reproduce its frozen USD ~10M Control result.

Counts and split totals agree, but this does not prove byte/float parity of
historical input values. This version finds the **first numerical difference**
before attempting another full backtest.

## Source and data contracts

TCC engine: source tag `v1.0.6`, commit
`c0d71772092f0c26c9f28f0211b9933e9c396b95` (not modified).

TCC official frozen data: `dados/pesquisa` from main commit
`f9cf29fdb736676d0d3e26780481be99813c602a`, snapshot SHA
`4e2fd225cc0ea05da56dad8f0628ca989ad332812a5fa3a7dc796b2b8a6d5128`.
The TCC **tag v1.0.6 itself does not contain the frozen CSVs**, which were
committed to the official TCC main afterward. All frozen file SHA-256 values
are checked from its manifest before reading.

MCT snapshots:
- #11: `20260925T003216-f836c087`
- #12: `20260925T113705-404cffea`

Their archived market-data aggregate signatures must agree. MCT data is read
from local MongoDB cache, **without an Alpaca request**, via the exact
RAW/SIP/1Day identity and 2016-01-01 through 2026-09-17 window.

## Safety

The data cache in MongoDB is mutable. Each MCT RAW asset is first checked
against the per-asset `raw_sha256` recorded by the archived #11 experiment
manifest. Its normalized OHLCV is checked against `sha256` from the same
manifest. A mismatch is reported `STALE_MCT_CACHE` or
`STALE_MCT_ACTIONS_OR_PREPARATION`. Such assets are **not** reported as
historical TCC-vs-MCT differences and must not be compared as if the old
snapshot were still available.

The script performs no Mongo writes, no Alpaca calls, no TCC writes and
no model fitting. It does not touch Strategy #11/#12, Soft, Winner,
Paper/Live or Model Tuning.

## Output

`scripts/audit_tcc_v106_fold1_data_parity.py` produces:
- `report.json`: provenance, hash checks, stale assets and status by stage;
- `summary.csv`: per-asset RAW, Corporate Actions, split, normalized OHLCV,
  and Fold-1 feature/target parity;
- `first_differences.csv`: example timestamps, fields and values;
- `tcc_v106_fold1_parity_audit.zip`: all three above.

Floats are first compared exactly, then with absolute/relative tolerance
1e-12. Tiny rounding differences are separated from substantive differences.

Features and forward targets are computed on each dataset by the same
verbatim TCC v1.0.6 code and inspected through 2020-04-24. This isolates
input/preparation parity. It does **not** assert model-fit parity.

## Example PowerShell usage

First obtain the archived #11 and #12 ZIP files from their completed jobs.
Check out a separate read-only working copy of the official TCC data:

```powershell
git clone https://github.com/betovlima/tcc_mba_usp_data_science_analytics.git C:\tcc_frozen_audit
git -C C:\tcc_frozen_audit checkout --detach f9cf29fdb736676d0d3e26780481be99813c602a
```

From the MCT API root, with its `.venv` activated:

```powershell
$env:PYTHONPATH="src"
python scripts/audit_tcc_v106_fold1_data_parity.py `
  --tcc-data "C:\tcc_frozen_audit\dados\pesquisa" `
  --strategy11-zip "C:\path\to\market_cycle_trader_20260925T003216-f836c087.zip" `
  --strategy12-zip "C:\path\to\market_cycle_trader_20260925T113705-404cffea.zip"
```

No new Simulation is required. If the MCT cache has changed, first recover the
old frozen MCT snapshot from a real existing backup, if available, or explicitly
report that exact snapshot parity cannot be determined from the exported ZIP
alone. Do not silently refresh or mix snapshots.
