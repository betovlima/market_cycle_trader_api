# MCT API v10.8.47 — Control-first Neural Meta-Veto

## Research question

The scientific Control remains the primary model benchmark at
**USD 5,887,904.38**. Under the fixed execution-feasibility assumptions,
v10.8.42 falls to USD 528,709.78 and v10.8.44 Liquidity-Aware recovers to
**USD 1,078,635.41**. v10.8.45 TinyTCN regression (USD 68,345.26) and
v10.8.46 pairwise Deep Ranking (USD 1,280.80) both failed because the
neural model replaced candidate-selection information that the Control
already handled much better.

v10.8.47 changes the role of Deep Learning completely:

> **Control chooses the action. Deep Learning may only veto an
> asset-to-asset rotation.**

The network never chooses an alternative asset, never overrides a HOLD,
never blocks entry from CASH and never blocks an exit to CASH.

## Fail-safe intervention rule

A fold must earn the right to intervene using only chronological
pre-OOS validation. The fixed candidate thresholds are 0.10, 0.20,
0.30 and 0.40 for P(candidate better than incumbent).

A threshold qualifies only when the validation subset contains:
- at least 50 proposed veto examples; and
- at least 60% precision at identifying a bad proposed rotation.

The most permissive qualified threshold is selected. If no threshold
qualifies, **intervention is disabled for that fold** and the path is
exactly the base v10.8.44 Liquidity-Aware Control.

This rule is fixed before viewing v10.8.47 OOS capital and cannot be
changed through Swagger.

## Neural input and target

A compact shared causal TinyTCN encoder receives:
- the candidate's last 40 completed-session causal feature vectors;
- the incumbent's last 40 completed-session causal feature vectors;
- three Control context values: candidate utility, incumbent utility
  and their utility gap.

Training samples are created only from the pre-OOS calibration segment.
The original calibration LightGBM top candidate is paired against each
lower-ranked possible incumbent. The binary meta-label is:

`accept = candidate forward_risk_adjusted_utility > incumbent forward_risk_adjusted_utility`

The full 60-session scientific utility label must mature strictly before
the fold test start. The final network is refit only on this already
matured calibration data after epoch count and intervention threshold
are selected from the chronological validation tail.

Important limitation: **this first meta-veto target is relative
scientific utility, not direct paired capital advantage**. A future
state-aware `delta capital accept-vs-veto` rollout is a different
hypothesis and must not be silently conflated with v10.8.47.

## Paired OOS execution and parity guard

The original fold-specific LightGBM Control fit/calibration remains
unchanged. Final utilities are transformed with the exact v10.8.44
prior-close liquidity overlay.

The same model campaign then runs two independent state-aware OOS paths:
1. `base_liquidity`: exact v10.8.44 behavior, neural veto disabled.
2. `meta_veto`: same base policy, veto enabled only in qualified folds.

Both use the same v10.8.42/v10.8.44 execution assumptions: whole shares,
no leverage, 10% volume capacity, ex-post execution-day volume cap,
assumed spread/impact, original fees, partial liquidation and residual
CASH, no forced terminal liquidation.

The job **aborts** unless the paired base path reproduces the completed
v10.8.44 ending capital USD 1,078,635.41 to within USD 0.000001.
