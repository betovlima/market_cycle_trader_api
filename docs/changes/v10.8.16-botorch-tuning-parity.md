# API v10.8.16 — BoTorch tuning parity with TCC

## Context

The TCC research line evolved the hyperparameter search in two separate layers:

1. deterministic space filling with SciPy Latin Hypercube Sampling;
2. adaptive CARO refinement using BoTorch SingleTaskGP with GPyTorch.

MCT already used SciPy `qmc.LatinHypercube` for its initial and recovery
space-filling proposals, so no replacement was needed in that layer.

The remaining parity gap was the adaptive CARO surrogate. MCT API 10.8.15
still used `sklearn.gaussian_process.GaussianProcessRegressor`, while the TCC
research branch `research/tiingo-lightgbm-botorch-caro-v2` had moved to
BoTorch/GPyTorch.

This release ports the reusable optimization improvements back into MCT while
preserving the MCT multi-metric Champion governance.

## Version and branch

- API: `10.8.16`
- branch: `feature/v10.8.16-botorch-tuning-parity`
- parent: `feature/v10.8.15-tcc-engine-parity`

## Hyperparameter exploration

The existing MCT Latin Hypercube implementation is retained:

```python
from scipy.stats import qmc
qmc.LatinHypercube(...)
```

This already matches the TCC methodology used by the LightGBM hyperparameter
campaign.

The MCT search-space normalization, structural constraints, deterministic seeds,
candidate de-duplication and frozen campaign protocol are unchanged.

## CARO surrogate migration

Previous MCT implementation:

```text
scikit-learn GaussianProcessRegressor
+ Matern kernel
+ one surrogate per economic metric
```

New implementation:

```text
BoTorch SingleTaskGP
+ GPyTorch ExactMarginalLogLikelihood
+ Standardize outcome transform
+ one surrogate per economic metric
```

The four MCT modeled outcomes remain:

- ending capital;
- Sharpe;
- maximum drawdown;
- worst-fold return.

The TCC single-objective experiment is therefore not copied literally.
Only the improved surrogate technology is ported; MCT keeps its richer
multi-metric research governance.

## CARO v2.1 acquisition behavior

The TCC audit found that an additive uncertainty bonus could make a highly
uncertain but weak region dominate Expected Improvement.

The MCT acquisition now follows the same principle as TCC CARO-BoTorch v2.1:

```text
constrained_expected_improvement
    × (1 + exploration_weight × normalized_uncertainty)
```

Uncertainty can therefore modulate a promising proposal but cannot create a
winner by itself.

If constrained Expected Improvement collapses across the entire pool, the
algorithm falls back to:

```text
P(beat Champion and satisfy risk constraints)
    × multiplicative uncertainty modifier
```

The acquisition mode is recorded as either:

- `multiplicative_constrained_ei`;
- `probability_fallback`.

## Local preference under low confidence

When the surrogate assigns less than 10% maximum probability of beating the
current Champion across the full candidate pool, proposal selection is
restricted toward the Champion trust region.

The default local radius is:

```text
max(0.08, trust_region_radius × 1.50)
```

At least the 64 closest candidates are kept eligible if the radius contains too
few proposals.

This reproduces the TCC v2.1 behavior that avoids drifting toward remote,
high-uncertainty regions when the model is pessimistic everywhere.

## Stagnation recovery

The default Unified CARO stagnation recovery threshold changes from 4 to 8
trials for new campaigns.

Existing campaign documents that explicitly persisted another value continue to
use their own configured value.

The global space-filling recovery path remains available and is still part of
Unified CARO.

## Device

BoTorch defaults to CPU in MCT for predictable production behavior.

Optional environment variable:

```text
MCT_BOTORCH_DEVICE=cpu
MCT_BOTORCH_DEVICE=auto
MCT_BOTORCH_DEVICE=cuda
```

`cuda` raises an explicit error when CUDA is unavailable. `auto` uses CUDA
only when PyTorch reports it available.

## New dependencies


## Diagnostics added to each adaptive proposal

The proposal now records:

- `surrogate = botorch_single_task_gp`;

- `botorch_device`;
- `acquisition_mode`;
- `low_confidence_local_mode`;
- `max_pool_probability_beats_champion`;
- `distance_to_champion_chebyshev`;
- `local_radius`;
- `candidate_pool_size_eligible`.

## Tests

The regression suite validates:

  fallback;
